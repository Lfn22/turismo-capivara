# REQUIREMENTS.md — Turismo Capivara v2.0

> Milestone: **v2.0 — Lançamento em Produção**
> Criado: 2026-06-26 — baseado na auditoria executiva do MVP (Comitê de 7 especialistas, 12 pilares)
> Status: Em andamento

**Escopo:** Tornar o CAPI MVP apto para lançamento com primeiros clientes pagantes e apresentável a investidores.
Cobre: hardening de infraestrutura, confiabilidade de email, integridade de pagamento PIX, UX do checkout, painel mobile, polimento público, SEO estruturado, testes E2E e observabilidade.

## Categorias

### Infraestrutura (INFRA) — Phase 21

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| INFRA-01 | Remover `ioredis` do `package.json` e artefatos de dev (`fix-plan06.js`, `.worktrees/`, `out/`) do repositório | `pnpm ls ioredis` retorna vazio; arquivos ausentes do git; CI passa |
| INFRA-02 | `validateEnv()` valida na inicialização: `R2_BUCKET_NAME`, `R2_PUBLIC_URL`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `ANONYMIZATION_SALT` (≥32 chars), `RESEND_API_KEY`, `EMAIL_FROM` | API encerra com erro descritivo se qualquer variável ausente; teste unitário cobre cada campo |
| INFRA-03 | JWT registrado com `expiresIn: '7d'`; CORS inclui método `PUT` na lista permitida | Token expirado retorna 401; `PUT /auth/reset-password` retorna 200 no browser sem CORS error |
| INFRA-04 | Endpoint `/health` executa `SELECT 1` e retorna `{ db: 'ok' }` ou HTTP 503 `{ db: 'unreachable' }` | Health check Railway monitora `/health`; DB offline → 503 em ≤5s |
| INFRA-05 | Fastify instanciado com `connectionTimeout: 10_000` e `keepAliveTimeout: 5_000` | Conexão ociosa encerrada após 5s; conexão nova recusada após 10s sem handshake |
| INFRA-06 | Todo log de request inclui `requestId` único (UUID via `genReqId`) propagado via header `X-Request-Id` | Grep de qualquer log de rota mostra campo `reqId`; header presente na response |
| INFRA-07 | Schedule do job de expiração corrigido de `* * * * *` para `0 * * * *` | Job executa uma vez por hora; log confirma execução horária em staging |
| INFRA-08 | `checkout.test.ts` portado de `.worktrees/capi-mvp-melhorias/` para `apps/api/src/__tests__/` | `pnpm test` na raiz executa checkout tests; todos passam; arquivo não existe mais no worktree |

### Email (EMAIL) — Phase 22

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| EMAIL-01 | `sendEmailWithRetry()` com 3 tentativas e backoff exponencial (500ms → 1s → 2s); todos os callers migrados de `void resend.emails.send()` para a nova função | Falha simulada na 1ª tentativa → 2ª tentativa em 500ms; falha total → erro logado, sem throw; grep confirma zero ocorrências de `void resend` |

### Integridade de Pagamento (PAY) — Phase 16

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| PAY-01 | Criação de booking PIX em `prisma.$transaction` com lock de slot (`FOR UPDATE`) — nenhum slot pode ter duas reservas ativas simultâneas | Teste de carga com 50 req concorrentes no mesmo slot → exatamente 1 booking criado |
| PAY-02 | `MP_ACCESS_TOKEN` validado via chamada real à API do Mercado Pago na inicialização da API | API encerra com `INVALID_MP_TOKEN` se token inválido; log indica causa |
| PAY-03 | Polling de status PIX com timeout de 30min e transição automática para EXPIRED | Booking sem confirmação de pagamento em 30min é marcado EXPIRED e slot liberado |
| PAY-04 | Slot liberado atomicamente em caso de falha na criação do pagamento Mercado Pago | Erro na API do MP → slot volta para disponível na mesma transação; sem slots "presos" |

### Confiabilidade Operacional (OPS) — Phase 19

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| OPS-01 | Job de expiração PIX usa `pg_try_advisory_lock` para prevenir execução duplicada em multi-instância | Duas instâncias em paralelo → apenas uma processa; lock liberado em `finally` |
| OPS-02 | Upload de arquivo só prossegue se variáveis R2 estão presentes e validadas (coberto por INFRA-02) | `R2_BUCKET_NAME` ausente → API não sobe; erro descritivo no log |
| OPS-03 | Email de confirmação de booking enviado com retry (coberto por EMAIL-01) | Booking confirmado → email enviado; falha na 1ª tentativa → retry automático |
| OPS-04 | `ToastProvider` registrado uma única vez em `_app` / layout raiz; nenhuma página duplica o provider | Ação em qualquer página dispara exatamente 1 toast; sem toasts duplicados |
| OPS-05 | Badge de status de destino (PENDENTE / APROVADO / REJEITADO + motivo) visível no painel do guia | Destino rejeitado exibe motivo da rejeição; badge muda de cor por status |

### UX do Checkout (UX) — Phase 18

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| UX-01 | Countdown PIX MM:SS visível durante espera de confirmação de pagamento | Timer inicia ao exibir QR code; chega a 00:00 e exibe mensagem de expiração |
| UX-02 | QR code PIX renderizado visualmente no frontend (não apenas código alfanumérico) | Usuário escaneia QR no mobile sem copiar texto |
| UX-03 | Link "/minha-reserva" exibido na tela de confirmação com bookingId preenchido | Link clicável redireciona para consulta de reserva correta |
| UX-04 | BookingForm protegido contra double-submit (botão desabilitado, `aria-busy`, spinner) | Cliques múltiplos no submit não criam bookings duplicados |
| UX-05 | CPF não exibido em texto plano após envio do formulário; campo limpo ou mascarado | DevTools não mostra CPF do turista na resposta ou estado do componente |

### Painel Mobile (MOB) — Phase 13

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| MOB-01 | Painel do guia usa card layout responsivo em telas ≤ 768px (sem tabelas horizontais) | Nenhum scroll horizontal no painel em iPhone SE (375px) |
| MOB-02 | Touch targets de botões e links no painel ≥ 44px | Auditoria Lighthouse: zero falhas de tap target size |
| MOB-03 | Todas as ações do painel (confirmar, cancelar, rejeitar) exibem toast de feedback | Ação sem conectividade exibe toast de erro; ação bem-sucedida exibe toast de sucesso |
| MOB-04 | Estados vazios com mensagem descritiva em todas as listagens do painel | Lista de reservas vazia → "Nenhuma reserva encontrada" com CTA; não tela em branco |

### Polimento e Dados Públicos (POL) — Phase 20

| ID | Requisito | Critério de Aceite |
|----|-----------|-------------------|
| POL-01 | Home pública exibe pelo menos 6 destinos aprovados | Página inicial com ≥6 destinos em produção; fallback se <6 disponíveis |
| POL-02 | Listagem de destinos filtra apenas status APPROVED por padrão | Destinos PENDING ou REJECTED não aparecem para turistas não autenticados |
| POL-03 | Acesso ao painel com tenant PENDING exibe mensagem clara de aprovação pendente | Guia com tenant PENDING vê "Sua operadora está em análise" em vez de 403 genérico |
| POL-04 | Super-admin tem paginação na listagem de tenants/operadoras | Listagem não carrega todos os registros de uma vez; paginação ≤ 20 por página |

| ID | Requisito | Critério de Aceite |

| QA-01 | Testes E2E com Playwright cobrindo 3 fluxos críticos: (1) reserva→PIX→confirmação, (2) login global, (3) expiração automática de booking | `pnpm e2e` passa os 3 fluxos em CI; qualquer quebra de fluxo bloqueia deploy |

## Fora de Escopo (v2.0)

- Pagamento por cartão de crédito — pós-PMF
- Reviews e avaliações de guias — sem dados reais ainda
- Chat turista↔guia — WhatsApp resolve no volume inicial
- App mobile nativo — web responsiva suficiente
- Multi-idioma — mercado inicial 100% PT-BR
- Repasse automático ao guia — manual aceitável no volume inicial
- Queue de email com BullMQ/Redis — `sendEmailWithRetry()` suficiente no volume inicial
- Analytics dashboard — volume insuficiente para justificar

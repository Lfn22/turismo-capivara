## Overview

**Objetivo:** Transformar o CAPI MVP em um produto apto para primeiros clientes pagantes e apresentável a investidores-anjo.

**Entrada:** MVP funcional com payments PIX, multi-tenant, painel do guia e interface do turista — com débitos técnicos identificados em auditoria (infraestrutura, segurança, confiabilidade, UX, qualidade).

**Saída esperada:**
- Infraestrutura limpa, sem dependências mortas ou artefatos de desenvolvimento
- Todas as variáveis críticas validadas na inicialização
- Emails com retry automático (zero fire-and-forget)
- PIX com criação atômica e lock de slot (zero overbooking)
- Checkout com UX completo (countdown, QR visual, proteção double-submit)
- Painel mobile responsivo com touch targets adequados
- SEO com JSON-LD estruturado nas páginas públicas
- Testes E2E cobrindo 3 fluxos críticos + auditoria de endpoints protegidos
- Uptime monitoring e backup verificado

**Estimativa total:** ~29h em sequência · ~22h com paralelismo (Fases 3 e 4 paralelas)

## Phase Details

### Phase 21: Hardening de Infraestrutura
**Goal:** Eliminar débitos técnicos de infraestrutura zero-risco em uma sessão (~2h) antes de qualquer outra execução.
**Depends on:** Phase 17 (Segurança e Dados — ✅ Completo)
**Requirements:** INFRA-01, INFRA-02, INFRA-03, INFRA-04, INFRA-05, INFRA-06, INFRA-07, INFRA-08
**Complexidade:** 2/10 · **Risco:** 1/10

**Success Criteria:**
1. `pnpm ls ioredis` retorna vazio; `fix-plan06.js`, `.worktrees/` e `out/` removidos do git
2. API encerra com erro descritivo se `R2_BUCKET_NAME`, `ANONYMIZATION_SALT`, `RESEND_API_KEY` ou `EMAIL_FROM` ausentes
3. `PUT /auth/reset-password` funciona no browser sem CORS error; JWT expira em 7 dias
4. `GET /health` retorna `{ db: 'ok' }` em condição normal; HTTP 503 se DB offline
5. Log de qualquer rota contém campo `reqId` com UUID; header `X-Request-Id` presente na response
6. Job de expiração executa às horas exatas (`:00`), não a cada minuto
7. `pnpm test` executa `checkout.test.ts` e todos os testes passam

**Plans:**

### Phase 22: Confiabilidade de Email
**Goal:** Eliminar o padrão fire-and-forget de email — garantir que falhas de entrega sejam retentadas e logadas.
**Depends on:** Phase 21 (INFRA-02 valida RESEND_API_KEY)
**Requirements:** EMAIL-01
**Complexidade:** 3/10 · **Risco:** 2/10

**Success Criteria:**
1. `sendEmailWithRetry()` existe em `apps/api/src/shared/email.ts` com 3 tentativas e backoff 500ms/1s/2s
2. Zero ocorrências de `void resend.emails.send` no codebase (grep confirma)
3. Falha simulada na 1ª tentativa → 2ª tentativa após 500ms (log registra `attempt: 2`)
4. Falha total nas 3 tentativas → erro logado com `{ err, attempt: 3 }`, sem throw não tratado

**Plans:**
- [ ] 22-01-PLAN.md — Implementar sendEmailWithRetry() e migrar todos os callers (T-06)

### Phase 16: Integridade de Pagamento PIX
**Goal:** PIX com criação atômica, lock de slot, validação de token MP na inicialização e liberação de slot em caso de falha.
**Depends on:** Phase 21 (infra limpa), Phase 22 (email confiável)
**Requirements:** PAY-01, PAY-02, PAY-03, PAY-04
**Complexidade:** 7/10 · **Risco:** 6/10

**Success Criteria:**
1. 50 requisições concorrentes no mesmo slot → exatamente 1 booking criado; demais recebem SLOT_UNAVAILABLE
2. API encerra na inicialização com `INVALID_MP_TOKEN` se `MP_ACCESS_TOKEN` inválido
3. Booking PIX sem confirmação em 30min → status EXPIRED, slot liberado automaticamente
4. Erro na API do Mercado Pago durante criação → slot liberado na mesma transação; nenhum slot "preso"

**Plans:**
- [ ] 16-01-PLAN.md — Transação atômica PIX + `SELECT FOR UPDATE` no slot (PAY-01, PAY-04)
- [ ] 16-02-PLAN.md — Validação MP_ACCESS_TOKEN na inicialização (PAY-02)
- [ ] 16-03-PLAN.md — Polling de status PIX + expiração em 30min (PAY-03)

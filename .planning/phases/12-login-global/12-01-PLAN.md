<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Password Reset Token → Email | Raw token transmitted via email (attacker can intercept) |
| Database → Token Hash | Token hash stored in database (hash must withstand DB breach) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Tampering | PasswordResetToken.hashedToken | mitigate | Store bcryptjs hash of raw token; never store raw token in DB. Use userId + hash lookup (not bcrypt.compare full-table scan per RESEARCH.md pitfall 1) |
| T-12-02 | Information Disclosure | PasswordResetToken via email | mitigate | Raw token sent via email (single-use, 1-hour TTL per D-08). Attacker with email access gains 1-hour window — acceptable per threat model |
| T-12-03 | Repudiation | Email unique constraint | accept | Global email uniqueness prevents multi-tenant account creation; acceptable tradeoff for unified login |
| T-12-04 | Denial of Service | Password reset spam | mitigate | Rate limiting applied per route (implemented in Plan 02 API routes) |
| T-12-05 | Elevation of Privilege | Token reuse | mitigate | usedAt field prevents single-use violation; API sets usedAt on consumption (Plan 02) |

</threat_model>
